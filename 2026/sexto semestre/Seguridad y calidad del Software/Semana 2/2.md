## Caso práctico — Transferencia bancaria

Caso real para comprender la diferencia práctica entre pruebas funcionales y no funcionales en un sistema bancario.

>[!summary]
>La hipótesis es un supuesto previo, por ejemplo: considerar que el usuario tiene acceso a internet.

### Perspectiva funcional

>[!question] ¿Se transfiere el monto correcto al destinatario correcto?

- **Validar que el monto se debite de la cuenta origen**
  - Prueba funcional basada en la documentación disponible.
- **Verificar que el mismo monto se acredite en la cuenta destino**
  - Validar que el usuario tenga un saldo igual o superior al monto a transferir.
  - En Chile: validar RUT y número de cuenta del destino.
- **Confirmar que los saldos se actualicen correctamente**
  - Prueba de integración entre las BD para asegurar correspondencia de datos y evitar duplicados o cargas erróneas.
- **Generar comprobante con datos precisos**
  - Verificar que los datos usados (RUT, institución, monto) se reflejen en una sola entidad comprobante.
- **Aplicar comisiones según política establecida**
  - Considerar las reglas del negocio: comisión según tipo de transferencia (mismo banco vs. bancos distintos).

### Perspectiva no funcional

>[!question] ¿El sistema soporta muchas transferencias simultáneas sin caídas?

- **Procesar miles de transacciones concurrentes**
  - Prueba de carga: estimar 1000 transacciones simultáneas y simular 500 para observar la reacción del sistema.
- **Mantener tiempos de respuesta menores a 2 segundos**
  - Asegurar que la tecnología no esté desactualizada y medir la latencia entre backend y frontend.
- **Garantizar seguridad con encriptación end-to-end**
- **Asegurar disponibilidad del 99.9 % del tiempo**
- **Proteger contra accesos no autorizados**

---

Resumen de requisitos no funcionales del caso:

1. **Seguridad** → Encriptación (en reposo y en tránsito)
   1. Validación de contraseñas.
   2. Código de validación por SMS → migrar a WhatsApp.
2. **Disponibilidad**
   1. Asegurar que el sistema esté disponible para realizar las transacciones.
3. **Servicio de transacciones**
   1. Verificar que el sistema de transacciones esté operando.

## Integración del cumplimiento de las pruebas

Hacer un documento con el cumplimiento de las pruebas, incluyendo capturas de pantalla como **evidencia** que nosotros como desarrolladores presentamos al cliente.

Explicar al área legal sin tecnicismos, para asegurar que se entienda que el sistema cumple con el marco legal.

- Los bancos tienen certificaciones para almacenar tarjetas y automatizar su uso.
- Cuentan con áreas **SOC** (*Security Operations Center*) con niveles que administran la mitigación de ataques de denegación de servicio (DoS) y fraudes al servicio.

>[!info] Programas para la seguridad
>
> - **OWASP** — estándares y buenas prácticas de seguridad.
> - **Grafana** — visualización e interpretación de datos.
> - **Datadog** — monitoreo y observabilidad.
> - **JMeter** — detección de cuellos de botella y tiempos de respuesta.
